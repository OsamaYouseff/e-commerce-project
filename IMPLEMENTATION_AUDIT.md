# PostgreSQL Migration Implementation Audit

**Status: all four passes resolved.** Every first-pass, second-pass, third-pass and code-review finding below now has a fix and a verification. The only item still open is operational, not code: the Node engine alignment in *Plan and operations inconsistencies*.

## Scope and verification

Reviewed the implementation against [the detailed migration plan](ARCHITECTURE_MIGRATION_PLAN.md), [the backend plan](backend/ARCHITECTURE_MIGRATION_PLAN.md), and the migration [runbook](backend/src/scripts/migration/RUNBOOK.md). The audit covered PostgreSQL schema/migrations, runtime wiring, use cases and repositories, auth middleware, migration mapping/import/reconciliation, and the deployment template.

`npm test` exits successfully with 84 named tests across nine files (auth middleware, field picking, legacy user validation, error mapping, HTTP validation, migration mapping, migration fingerprint, checkout pricing, and the repository query-double suite). The database-backed conformance suite runs 106 checks and passes against both environments (`:5002` on `evo_market_prod` and `:5003` on `evo_market_staging`), including the coupon, shipping, idempotency-conflict, stale-preview-refusal, partial-cart, cart-delete and numeric-string checks. The harness selects its target with `BASE_URL` and its admin-elevation database with `DATABASE_URL`; both are required, and pointing them at different databases fails admin elevation rather than skipping. `npm run test:integration` adds 32 tests against a real PostgreSQL server — 13 parallel-request tests plus 19 schema/constraint/transaction tests that build and drop their own database — and skips them when `INTEGRATION_DATABASE_URL` is unset.

Migration tooling was exercised against the committed snapshot: `import-mongo.js --reset --insert` into `evo_market_test` imports all 21 products / 1 order / 1 order line with no failures, no defaulted timestamps and the two documented orphan quarantines, and `reconcile-import.js` then reports `missing=0 extra=0` for every collection with zero fingerprint mismatches (the run is `WARN` only because of the expected quarantined wishlist line, matched by `--quarantine-expect`). Both frontends build with `vite build`.

The unit tests still do not exercise real concurrent mutations; the lock changes are covered by the conformance suite's create-twice and duplicate-create checks and, in the third pass, by twelve parallel-request tests in `test/integration/concurrency.test.js` against a real PostgreSQL server. Integration coverage is deliberately not a substitute for a rehearsal: `test/integration/` asserts invariants, it does not migrate real Mongo data or exercise the backup/restore roundtrip.

The first-pass findings below describe issues found before the latest edits. Several are now addressed in the visible code; the second-pass findings at the end of this document supersede them for current status.

## Findings

### P1 — Checkout accepts browser-authored prices, totals, and shipping details

In [orders.usecases.js](backend/src/modules/orders/application/orders.usecases.js#L8), order items take `priceAtOrderInCents` from the request, and the repository inserts the request's financial totals and shipping address directly in [orders.repository.js](backend/src/modules/orders/infrastructure/orders.repository.js#L74). The code does not require a non-empty item list, recalculate prices from PostgreSQL, or verify that the supplied address belongs to the authenticated user. The JWT-derived user ID is used, but the financial and shipping facts remain client-controlled. This conflicts with plan sections 17–19 and ADR-7.

**Fix:** Validate a non-empty list of product IDs and positive integer quantities; load the products and an address owned by `req.user.id`; calculate line prices, subtotal, discount, shipping, and total on the server; take snapshots from those database rows; reject unsupported payment methods; and add an idempotency key for checkout retries. Keep all order writes in one transaction.

The detailed plan also requires clearing the cart in that transaction. The runbook instead records a deliberate decision to clear it in a separate frontend request. Choose one behavior and update both documents: the current split request can leave a purchased cart uncleared or allow a retry to create a duplicate order.

### P1 — Import can fail on missing timestamps and drops the legacy delivery date

[mapping.js](backend/src/scripts/migration/mapping.js#L204) maps absent `createdAt`/`updatedAt` values to `null`, while the SQL schema declares those columns `NOT NULL`. The importer explicitly includes those columns in its inserts, so the PostgreSQL defaults do not apply to explicit `NULL` values. The mapping also reads `o.estimatedDeliveryAt`; the legacy order schema stores this as `shippingInfo.estimatedDeliveryDate`, so an existing delivery date is lost on import.

**Fix:** Map `shippingInfo.estimatedDeliveryDate`; for missing timestamps, choose the documented fallback and emit a per-record report entry, or omit the timestamp column from that row's insert so the database default applies. Add mapping and import cases for both conditions.

### P1 — Reconciliation is not a sufficiently strict cutover gate

[reconcile-import.js](backend/src/scripts/migration/reconcile-import.js#L200) checks parent ID sets, but child tables are compared mainly by counts and numeric rollups; it does not prove that each cart/wishlist/order item retains its product reference and position. PostgreSQL integrity findings are counted as warnings. Without `--strict`, extras or integrity warnings can produce a non-`PASS` report while the process exits with status 0 ([exit logic](backend/src/scripts/migration/reconcile-import.js#L230)). The importer also uses `ON CONFLICT DO NOTHING` and a count-based checkpoint (`existing >= expected`) in [import-mongo.js](backend/src/scripts/migration/import-mongo.js#L122) and [import-mongo.js](backend/src/scripts/migration/import-mongo.js#L284); that can silently accept rows already present under the same ID but with different data.

**Fix:** Compare exact source/target values or stable per-row fingerprints for parent and child rows, including ordered child references. Treat every unapproved extra, mismatch, or integrity warning as a non-zero result. Make the importer verify that conflicting target rows match the source before calling a phase complete, and bind checkpoints to a source snapshot fingerprint. The cutover runbook should require both `result === PASS` and a successful exit status.

### P1 — Password changes can partially write or lose password history

[updatePassword](backend/src/modules/users/infrastructure/users.repository.js#L105) reads the user, deletes all history rows, reinserts history rows, and updates the user password through separate queries without a transaction. A failure between these statements can erase or truncate history; simultaneous password changes can overwrite one another's history. This conflicts with the plan's transaction and password-history requirements.

**Fix:** Run the full password-change workflow in one transaction, lock the user row while reading/comparing the current password and recent history, then replace the bounded history and update the password using the same checked-out client. Return only the safe response.

### P1 — Public paginated product listing includes disabled products

The public `GET /api/products/all` handler calls [listPaginated](backend/src/modules/products/infrastructure/products.repository.js#L125), whose query selects every product without an `is_deleted = false` predicate. The filtered list, search, and single-product lookup do exclude disabled products. The runbook's Phase 6 contract says disabled products are hidden, so `/all` leaks disabled catalog entries and behaves differently from the other public endpoints.

**Fix:** Apply the public visibility predicate to the paginated query and its total count. If admins need disabled rows, expose a separate admin query with explicit authorization. Add a contract case that disables a product and checks every public catalog route.

### P2 — Cart, wishlist, and default-address writes have race conditions

Cart item replacement deletes and reinserts rows without locking the cart ([carts.repository.js](backend/src/modules/carts/infrastructure/carts.repository.js#L45)); concurrent updates can overwrite one another. Cart creation checks for an existing cart before opening a transaction ([carts.usecases.js](backend/src/modules/carts/application/carts.usecases.js#L37)), while `ON CONFLICT DO NOTHING` can return `null` ([carts.repository.js](backend/src/modules/carts/infrastructure/carts.repository.js#L27)); the caller then dereferences the missing cart. Wishlist creation has a similar check-then-insert race. Address creation counts defaults before insert and relies on the unique index to reject simultaneous first/default address writes, which currently becomes an unhandled database error.

**Fix:** Serialize mutations by locking the owning cart/wishlist/user row inside the transaction. Make create operations return or reload the winning row on uniqueness conflicts, and translate expected races to a stable conflict response or retry. Keep unique indexes as the final invariant guard and test concurrent create/update/default-switch operations.

### P2 — Cloudinary cleanup can delete the image now referenced by PostgreSQL

In [products.usecases.js](backend/src/modules/products/application/products.usecases.js#L69), the `try` block includes both saving the new image URL and deleting the old image. If old-image deletion fails after the database update succeeds, the `catch` deletes the newly uploaded image even though PostgreSQL now points to it. Product deletion also removes the Cloudinary image before deleting the row ([products.usecases.js](backend/src/modules/products/application/products.usecases.js#L87)), so a database failure can leave a product with a broken image. This is opposite to the plan's persist-then-clean-up sequence.

**Fix:** Compensate by deleting the new upload only when the database write fails. After a successful write/delete, enqueue or log idempotent cleanup of the old asset and retry failures separately. Add tests for upload failure, SQL failure, and old-asset deletion failure.

### P2 — Request validation and pagination bounds are incomplete

Product and address handlers pass most input directly into repositories. Database `CHECK`/`NOT NULL` failures become generic 500 responses in [error-middleware.js](backend/src/shared/http/error-middleware.js#L10), rather than the plan's 400 validation response. Product/order pagination parses query strings but does not enforce page ≥ 1 or the planned maximum limit of 100 ([products.router.js](backend/src/modules/products/http/products.router.js#L42), [orders.router.js](backend/src/modules/orders/http/orders.router.js#L64)); negative or very large limits can fail queries or request excessive work. Invalid address labels likewise reach the database constraint.

**Fix:** Add route-level schemas and business validation for IDs, quantities, product fields, labels, order values, page, and limit. Bound limits at 100, reject malformed input as 400, and map named database constraints to safe client errors.

## Plan and operations inconsistencies

- The detailed plan specifies normalized password history, while the shorter backend plan says it is a `text[]`; implementation follows the normalized table. Keep one canonical schema decision and make both plans agree.
- The detailed plan requires atomic checkout/cart clearing, while the runbook explicitly accepts a separate frontend clear request. Update the detailed plan or implement the transactional behavior; document the residual retry/failure risk either way.
- [backend/.env.example](backend/.env.example#L3) still describes MongoDB as the runtime database and `DATA_MODE=mongo` as the default, even though the current runtime env config is PostgreSQL-only. The runbook calls this template authoritative. Replace the stale Mongo/runtime instructions with the actual PostgreSQL-only variables before an operator uses it.
- The package declares Node `^22.22.0`, while the audit environment is Node `v20.20.0`; deployment runtime compatibility and the two lockfiles (`package-lock.json` and `yarn.lock`) still need to be aligned as required by the plan.

## Recommended fix order

1. Make checkout server-authoritative and verify address ownership; settle the cart-clearing decision in both plans.
2. Correct importer timestamp/date mapping and make reconciliation fail closed on any unexplained mismatch.
3. Make password history, cart/wishlist mutations, and default-address changes safe under failures and concurrent requests.
4. Hide disabled products from `/all`, isolate Cloudinary cleanup from committed database updates, and add bounded request validation.
5. Reconcile the operational docs/runtime and add database-backed tests for the repaired invariants before cutover.

## Second-pass re-audit — outstanding issues

### P1 — Import fingerprints mismatch valid PostgreSQL numeric values and skip password hashes

[fingerprint.js](backend/src/scripts/migration/fingerprint.js#L18) compares mapped values with `JSON.stringify` equality. The source maps `products.price` and order financial `BIGINT` values as JavaScript numbers, while node-postgres returns PostgreSQL `numeric` and `bigint` as strings by default. Thus ordinary values such as `12` and `"12.00"` compare unequal. `verifyPhase` will record a mismatch after inserting valid product rows, and reconciliation will report valid product/order rows as divergent. The user parent fingerprint also omits `password_hash`, so a wrong imported login hash is not detected. In addition, [verifyPhase](backend/src/scripts/migration/import-mongo.js#L160) only compares returned rows; it does not fail when an expected source ID is missing but unrelated target rows make the table count large enough to skip the phase.

**Fix:** Normalize values by PostgreSQL type before comparison (including fixed-scale decimals and 64-bit integers), compare password hashes through a redacted keyed fingerprint, and explicitly compare the full expected ID set with the fetched target ID set. Add tests using the actual node-postgres result types and a missing-ID/extra-row fixture.

### P1 — Storefront still offers a payment method the backend rejects

The checkout UI still offers `credit_card` in [CompleteCheckoutModal.jsx](frontend/evo_market/src/Components/CartPage/CompleteCheckoutModal/CompleteCheckoutModal.jsx#L345), but [orders.usecases.js](backend/src/modules/orders/application/orders.usecases.js#L10) accepts only `cash_on_delivery`. Selecting the visible card option now makes order creation return 400. The plan correctly says not to imply payment processing where no charge flow exists, but the customer-facing choice and backend contract must agree.

**Fix:** Until card processing is implemented, hide or disable the card option and explain the available method in the checkout UI. If card payments are supported later, add the provider flow and only then accept that method.

### P1 — The production storefront does not send an idempotency key

The new order ID is deterministic only when `body.idempotencyKey` is supplied ([orders.usecases.js](backend/src/modules/orders/application/orders.usecases.js#L92)). The current storefront builds `orderData` without that property in [CompleteCheckoutModal.jsx](frontend/evo_market/src/Components/CartPage/CompleteCheckoutModal/CompleteCheckoutModal.jsx#L81), so network retries still generate a fresh ID and can create duplicate purchases. Also, the server does not bind a key to a request fingerprint: reusing one key with a different cart/address silently returns the first order. The retry path revalidates current products and address before checking for the already-created order, so a replay can fail after a product is disabled or the address is removed.

**Fix:** Generate one stable key per checkout attempt in the client and reuse it for retries. Persist/compare a redacted request fingerprint with the key; reject a changed payload with 409. Look up an existing key before revalidating mutable catalog/address state, while still scoping it to the authenticated user.

### P2 — Non-empty wishlist creation silently discards every product

[wishlists.router.js](backend/src/modules/wishlists/http/wishlists.router.js#L9) validates and passes `products` as an array of ID strings. [wishlists.usecases.js](backend/src/modules/wishlists/application/wishlists.usecases.js#L28) still treats each entry as an object and reads `p.productId`; every string therefore becomes `undefined` and is filtered out. The current storefront initializes an empty wishlist, which hides this bug in the usual path, but callers that create a populated wishlist lose its requested items without an error.

**Fix:** Make the route and use case agree on one input shape, then add a non-empty `POST /api/wishlist` contract test that checks the returned and persisted product IDs.

### P2 — Cart and wishlist locks do not cover all mutation paths or concurrent creation

`createCart` and `createWishlist` check for an existing row before acquiring their advisory lock and do not re-check after acquiring it. Their repositories use `ON CONFLICT ... DO UPDATE`, so a second concurrent create can receive the first request's row and replace its items instead of returning the documented "already exists" result ([carts.usecases.js](backend/src/modules/carts/application/carts.usecases.js#L47), [wishlists.usecases.js](backend/src/modules/wishlists/application/wishlists.usecases.js#L28)). Wishlist `removeProduct`, `clearWishlist`, and `deleteWishlist` do not acquire the same lock used by `addProduct`, so those operations can still race and lose changes. Checkout also deletes cart items through the repository without taking the cart advisory lock, so it can interleave with an add/update request.

**Fix:** Re-check existence after taking the per-user lock; preserve the existing row without replacing its contents on duplicate create. Use the same lock in every wishlist mutation and in checkout before modifying the cart. Remove only the purchased quantity, or validate that checkout represents the full cart, and update the cart timestamp when checkout changes it.

### P2 — Import reports missing timestamps twice

The mapper adds missing timestamps to `report.defaultedTimestamps` before import ([import-mongo.js](backend/src/scripts/migration/import-mongo.js#L266)); `insertTable` adds the same row/fields again while omitting the timestamp columns ([import-mongo.js](backend/src/scripts/migration/import-mongo.js#L152)). Preview output has one record, but a real import duplicates each fallback entry, making the audit report overstate affected rows.

**Fix:** Record fallback metadata in one layer only and test the final import report, not just the pure mapper output.

### P1 — Checkout rejects valid coupons and records zero shipping

The storefront advertises working `10OFF` through `50OFF` coupons and calculates shipping as $20 below a $50 subtotal ([GeneralVariables.jsx](frontend/evo_market/src/General/GeneralVariables.jsx#L62), [GeneralFunctions.js](frontend/evo_market/src/General/GeneralFunctions.js#L98)). [CheckoutPanel.jsx](frontend/evo_market/src/Components/CartPage/CheckoutPanel.jsx#L34) sends the resulting discount and shipping amounts in cents. The backend rejects every positive discount as unsupported, so applying any listed coupon makes order creation fail with 400; otherwise it unconditionally stores discount and shipping as zero ([orders.usecases.js](backend/src/modules/orders/application/orders.usecases.js#L45)). A cart below $50 therefore shows a $20 shipping charge to the customer but saves an order with no shipping charge. Single-product checkout also sends the storefront's calculated shipping amount, which the backend ignores.

**Fix:** Define one server-side pricing policy. Validate coupon codes and calculate discount and shipping from authoritative product prices on the server; persist and return those computed totals. If discounts or shipping rules are not supported, remove the corresponding storefront choices and display only the actual server policy. Do not use client-submitted totals as the source of truth.

### P1 — Admin product create and price/stock edits are rejected by backend validation

The admin product form stores the values from both numeric inputs as strings (`e.target.value`) and submits `formData` directly ([ProductForm.jsx](frontend/admin_dashboard/src/Components/DashboardSections/ProductsPage/ProductForm/ProductForm.jsx#L145)). The API validator requires `price` to be a JavaScript number and `amount` to be an integer ([validation.js](backend/src/shared/http/validation.js#L40)); the product routes apply that validator to create and update requests ([products.router.js](backend/src/modules/products/http/products.router.js#L9)). As a result, creating a product or changing either numeric field sends string values and receives 400. An edit that changes only a non-numeric field can still pass if the untouched values retain their original numeric types.

**Fix:** Convert and validate numeric form values before submission, or normalize numeric strings in the backend validation boundary while rejecting empty, non-finite, fractional stock values, and invalid ranges. Verify create and partial-update requests using the exact payloads emitted by the admin form.

### P2 — Checkout modal displays shipping cents as whole dollars

[CompleteCheckoutModal.jsx](frontend/evo_market/src/Components/CartPage/CompleteCheckoutModal/CompleteCheckoutModal.jsx#L42) interpolates `shippingCostInCents` directly after the dollar sign. The cart sends 2000 for the storefront's $20 shipping fee, so the modal displays `$2000` instead of `$20` for orders below the free-shipping threshold. Other monetary rows in this modal convert cents to dollars.

**Fix:** Convert the shipping amount from cents to dollars using the same formatter as the subtotal and order total, and check both zero and non-zero shipping cases.

## Resolution summary

### Second pass

- **Import fingerprints** ([fingerprint.js](backend/src/scripts/migration/fingerprint.js)): values are normalized by PostgreSQL type family before comparison. `numeric` money rounds to two decimals, integer columns become canonical decimal strings (so 64-bit values above 2^53 stay exact and `42.0` cannot match `42` on a whole-number column), booleans accept `t/f/true/false/1/0`, and timestamps compare as instants. `password_hash` is compared through an HMAC digest (`MIGRATION_HASH_SALT`, process-stable fallback) instead of being skipped, for both `users` and `user_password_history`, and no report contains a raw hash. `diffIdSets` compares the full expected source ID set against the fetched target ID set in `verifyPhase`, for parents and for each child's parent id, so a missing row fails even when unrelated target rows keep the table count high. Child rows are ordered numerically, not lexicographically, so a parent with ten or more children cannot fingerprint differently by ordering alone. Covered by [fingerprint.test.js](backend/test/unit/fingerprint.test.js) (12 tests) using real node-postgres string types, a missing-ID/extra-row fixture and a 10-child ordering case.
- **Duplicate timestamp records** ([import-mongo.js](backend/src/scripts/migration/import-mongo.js)): the mapper is the only layer that records defaulted timestamps; `insertTable` no longer re-adds them. A real import report shows `defaultedTimestamps: []` with no duplicates.
- **Payment method**: the card toggle is gone from [CompleteCheckoutModal.jsx](frontend/evo_market/src/Components/CartPage/CompleteCheckoutModal/CompleteCheckoutModal.jsx). Checkout shows cash on delivery with a note that card payment is not available yet, matching the only method the API accepts.
- **Idempotency**: `newIdempotencyKey()` (crypto.randomUUID with a `getRandomValues`/random fallback) creates the key value, and `getCheckoutIdempotencyKey`/`rotateCheckoutIdempotencyKey` (GeneralFunctions.js) keep it in `sessionStorage` per customer rather than in a component ref. The checkout modal unmounts as soon as a request is sent, and it also unmounts on a page reload, so a ref lost the key exactly when a retry after a timeout needed it and a second order could be created. The stored key survives both and is rotated only once an order is confirmed to exist; when storage is unavailable the helpers fall back to a per-render key rather than breaking checkout. The key is sent as `idempotencyKey`. The API derives the order id from `sha256(userId|key)`, looks it up *before* revalidating catalog and address state, and compares `orders.request_fingerprint` (new column, migration `1700000000003_order_checkout_metadata.cjs`) with the new request: a retry returns the original order, and the same key with a different payload is a 409. The fingerprint covers items, address, coupon and payment method but not client totals, so a stale preview cannot turn a retry into a conflict. Covered by [checkout-pricing.test.js](backend/test/unit/checkout-pricing.test.js) and two conformance checks.
- **Wishlist creation**: `sanitizeProductIds` accepts the id strings the route validates (and still tolerates `{ productId }` objects), so a non-empty create stores what it was asked to store; the conformance suite creates a wishlist with a product and reads it back.
- **Locks and cart contents**: `createCart`/`createWishlist` re-check existence *after* taking the per-user advisory lock, so a concurrent create can no longer receive the first request's row and replace its items. `removeProduct`, `clearWishlist` and `deleteWishlist` take the same wishlist lock as `addProduct`. Checkout takes the cart lock before touching the cart and now calls `removePurchasedItems`, which subtracts exactly the purchased quantities (deleting rows that reach zero) and stamps `carts.updated_at`. `deleteCart` also runs in a transaction and takes the same per-user lock; without it, deletion's cascade could race an add and fail on the `cart_items` foreign key. The storefront re-reads the cart after checkout instead of calling `clearCart()`, so unpurchased items stay visible. Covered by a concurrency test that proves the delete blocks while the cart lock is held, plus conformance checks for duplicate create, key reuse and partial checkout (buying 1 of 3 leaves 2).
- **Server-side pricing** ([checkout-pricing.js](backend/src/modules/orders/application/checkout-pricing.js)): the API validates `10OFF`/`15OFF`/`20OFF`/`25OFF`/`50OFF` (case-insensitive, unknown code is a 400 rather than a silent zero), computes the discount from catalog prices, charges $20 below a $50 subtotal and free at or above it, persists the computed totals and `orders.coupon_code`, and returns them. Client `financials` is only compared. A preview that no longer matches the authoritative total is **refused**: nothing is written and the API answers 409 with `details.staleCart` and the real `financials`, so the storefront can show the customer both figures and have them confirm. The retry carries `acceptPricingChange: true` and the reported totals, reuses the same idempotency key, and is still priced by the server. The comparison is unconditional: the flag records that the customer agreed to a figure, it does not waive the check, so a price that moves again before the retry is refused again and asked about again. Per-product quantities are also validated after duplicate `productId` lines are aggregated, so repeated lines cannot reach a quantity no single line could carry. A client that sends no preview is unaffected. `GeneralVariables.jsx`/`GeneralFunctions.js` mirror the policy for the preview, so the two files must be changed together.
- **Admin numeric fields**: `validateProductInput` normalizes numeric strings at the boundary and returns the normalized payload, which the product routes now pass to the use cases; empty, non-numeric, non-finite, fractional-stock and out-of-range values are still rejected. A blank rating is now normalized to the numeric default `0` at the boundary and in the form (both `numericFormData` and the Reset action), because the cleared field used to pass validation as `""` and fail an otherwise valid create against the numeric column; an explicit `null` still means "leave unchanged" on a partial update. [ProductForm.jsx](frontend/admin_dashboard/src/Components/DashboardSections/ProductsPage/ProductForm/ProductForm.jsx) also converts price/stock/rating before submitting and refuses to submit unusable values. Covered by three HTTP-validation tests plus conformance checks for create, partial update and fractional stock.
- **Shipping display**: the checkout modal converts `shippingCostInCents` with `convertCentsToDollars` like the other rows, so $20 renders as `$20.00` and free shipping as `Free`.

### First pass

Checkout prices, discounts, shipping, quantities and address ownership are derived server-side; migration mapping preserves timestamps/line numbers/dates; reconciliation fails closed and reports id-set and fingerprint diffs; password changes write user and history atomically; disabled products are hidden from the public listing; Cloudinary cleanup happens only after a successful commit; and request validation and pagination bounds were tightened. `backend/.env.example` now documents PostgreSQL only.

### Third pass — test coverage the plan asked for

The backend plan's test section required two things that had no automated evidence: repository unit tests driven by an injected query double, and a parallel-request test for the per-user advisory locks. Both now exist.

- **Repository tests with a query double** ([repositories.test.js](backend/test/unit/repositories.test.js), 17 tests): every statement is asserted to have exactly one bound value per `$n` placeholder and no interpolated string; `orders.update` is asserted to write exactly the 15 allowlisted columns once each while ignoring hostile keys (`id`, `user_id`, `total_amount_in_cents`, `deleted_at`, unknown fields inside `financials`/`shippingAddress`/`shippingInfo`); a body with no allowlisted field reads instead of writing; `removePurchasedItems` is pinned to decrement a partial purchase and delete a fully purchased line, and to be a pure no-op for an empty purchase; `replaceItems` must bind position-ordered values. [withTransaction](backend/src/shared/database/transaction.js) is loaded against a stub pool to assert `BEGIN`/`COMMIT`/`release` on success, `ROLLBACK`/`release` and a rethrow on failure, and that the original error survives when `ROLLBACK` itself fails.
- **Concurrency tests against PostgreSQL** ([concurrency.test.js](backend/test/integration/concurrency.test.js), 10 tests, `npm run test:integration`): four parallel `POST /api/carts` with *different* products leave one cart holding only the winner's line; three parallel add-to-cart calls keep all three lines; the same product added to a wishlist three times in parallel is stored once with a single wishlist; a parallel mix of wishlist add/remove/add/add converges with no duplicate, no lost add and no resurrected removal; an in-flight partial checkout (buy 3 of 5) running against a concurrent add leaves exactly `2` and the new line, and the order is priced from the catalog rather than the client's claimed cent; a stale preview is refused with `409` carrying the authoritative totals and leaves both the order and the cart untouched, and accepting that total with the same key then creates the order; three parallel checkouts with one idempotency key produce one `201`, two `200` replays, one order and one line; reusing the key with a different payload is a `409`; a cart delete is proven to block while the per-user cart lock is held by a second connection, and the concurrent add that follows leaves no orphan `cart_items` row; three parallel default-address creates leave exactly one default row.
- **Mutation check**: with `pg_advisory_xact_lock` replaced by a no-op, 5 of the 8 concurrency tests fail (parallel cart create, parallel add-to-cart, duplicate wishlist add, concurrent wishlist add/remove, parallel default address). The three that still pass are held by database constraints and `ON CONFLICT (id) DO NOTHING` rather than by the lock: the partial-checkout pair is additionally protected by row locks on `cart_items`, and the two idempotency cases never raced on a cart. They are invariants worth keeping, but the lock itself is only what the first five detect.
- **Schema, constraint and transaction tests** ([schema.test.js](backend/test/integration/schema.test.js), 19 tests): the file creates its own randomly named database from `INTEGRATION_DATABASE_URL` (reusing only the host and path), applies `db/migrations` with node-pg-migrate, and drops it afterwards, so no environment database is touched. It asserts all four migrations are recorded and all eleven tables exist; the `pg_trgm` extension and `products_title_trgm_gin` are installed; `request_fingerprint` and `coupon_code` exist and accept NULL for legacy rows. Bad data is rejected by SQLSTATE: `23514` for a non-hex or uppercase id, a negative price/stock/rating, a zero or negative cart or order-line quantity, a negative order subtotal/discount/shipping, an unknown order status, and an unsupported shipping label (both `cancelled` and `canceled` are still accepted); `23505` for a second cart, wishlist or default address, a duplicate cart or wishlist line, and a repeated order line number; `23502` for a missing required column; `23503` for orphans in every direction. Deleting a user cascades to cart, cart lines, wishlist, wishlist lines, addresses, orders, order lines and password history while leaving the catalog intact; deleting a product `SET NULL`s the order line but keeps the order and its title/price snapshots. A `withTransaction` that throws after three inserts leaves the table counts unchanged, and because the pool is built with `max=1` the following transaction proves the client was released; a unique violation inside a transaction surfaces as `23505` and rolls the whole thing back. Finally all migrations roll down (no tables and no `pg_trgm` left) and back up, after which the constraints still reject a negative price.
- `npm test` runs `test/unit/` only (84 tests); `npm run test:integration` runs both database files (29 tests) and skips them when `INTEGRATION_DATABASE_URL` is unset, so the default command stays runnable without a database.

### Fourth pass — findings from the static code review

All five findings in [CURRENT_CODE_REVIEW.md](CURRENT_CODE_REVIEW.md) were reproduced in the code before being fixed.

- **P1 — the checkout modal threw on open**: `CompleteCheckoutModal.jsx` called `newIdempotencyKey()` without importing it, so mounting it raised a `ReferenceError` and checkout could not be opened at all. Fixed by importing it alongside the other `GeneralFunctions.js` helpers.
- **P1 — a changed price was charged without the customer seeing it**: `createCustomerOrder` discarded `response.data` and returned only a generic success, so the thunk's `response.staleCart` check could never fire. Two changes were needed, not one. The wrapper now passes the order through, and the *server* no longer creates an order whose preview disagrees with its own total: it answers `409` with `details.staleCart` and the authoritative `financials` before writing anything, and the modal shows both figures and retries with `acceptPricingChange: true` and the same idempotency key. `ApiError.conflict` gained a `details` argument so a 409 can carry them, and `createCustomerOrderReducer` returns the refusal untouched instead of toasting it as a failure. Covered by a concurrency test (a refusal creates no order and empties no cart, the accepted retry creates one) and five conformance checks.
- **P1 — the idempotency key was lost on retry**: the key lived in a `useRef`, and the modal is unmounted by `CartPage` as soon as the request is sent, so a timeout or reload produced a new key and could create a second order. The key now lives in `sessionStorage` per customer (`getCheckoutIdempotencyKey`), is rotated only after a confirmed order (`rotateCheckoutIdempotencyKey`), and falls back to a per-render key if storage is unavailable. The modal also stays open until the outcome is known and disables the button while in flight, instead of closing and unmounting mid-request.
- **P2 — a blank rating made a valid new product fail**: the form's Reset set `rating: ""`, which passed validation and reached a numeric column as an empty string. Both layers now use the numeric default: `validateProductInput` normalizes a blank rating to `0` (an explicit `null` still means "leave unchanged" on a partial update) and the form converts it before submitting.
- **P2 — cart deletion ignored the lock**: `deleteCart` deleted the row directly, so its cascade could race an add and fail on the `cart_items` foreign key. It now resolves the customer's cart, runs in a transaction, and takes the same per-user advisory lock, so it serializes against that owner's mutations. Covered by a concurrency test that holds the cart lock from a second connection and asserts the delete *blocks* on it; removing the lock fails that test on every run.

  While fixing this, a second defect on the same route surfaced: `DELETE /api/carts/:id` was unreachable for regular users. `verifyTokenAndAuthorization` only lets a caller pass their own id in the path, but the route forwarded that value to the use case as a *cart* id, and no cart row is keyed by a user id — so every customer request matched nothing and answered 404, and only an admin could ever reach the delete. The route now takes the customer's id like every sibling cart route (`find`, `add_update-product`, `remove-product`, `clear`, `cart_detailed_products`), and `deleteCart` looks the cart up by `user_id`.

A second review pass found three further defects in that first round of fixes, a third found three more, and a fourth found two. All nine are resolved.

- **P1 — a second price change was accepted without confirmation**: `acceptPricingChange: true` skipped the stale-total check outright, so a total that moved *again* after the customer confirmed the first one was simply charged, and the successful response still carried `staleCart: true`, which the storefront read as a request to confirm an order that already existed. The comparison is now unconditional — the flag records agreement to a figure, it does not waive the check — so the retry is priced and compared like any other attempt and a further move is refused again, with the same key, and asked about again. Only a placed order reports success, so the `staleCart` flag and the wrapper branch that interpreted it on a 2xx are gone. The storefront already re-armed its confirmation dialog from each refusal, so it needed no change. Covered by a concurrency test that moves a product between the refusal and the retry and asserts a second 409, no order, and one order for the whole sequence, and by five conformance checks including one that proves the flag alone does not buy the order.
- **P2 — the idempotency fallback rotated the key on every render**: when `sessionStorage` was unavailable the helper returned a fresh random key per call, and the modal reads it during render, so any state update mid-attempt changed the key and a retry after a lost response could create a duplicate order in exactly the browsers that cannot use storage. The fallback is now a module-scope `Map` keyed by customer, so the key is stable for the page session and survives the unmount that storage would otherwise have survived; rotation clears both copies. Verified against the real module with `sessionStorage` forced to throw: 500 re-renders and a simulated unmount keep one key, the pre-fix code fails four of those checks.
- **P2 — duplicate order lines bypassed the quantity limit**: each raw line was checked against `MAX_QUANTITY` (999) before quantities were summed, so 100 lines of 999 for one product became a single persisted line of 99,900 — far beyond what the cart API will accept for that product. The limit is per product, so it is now enforced again on the aggregated quantity. Covered by a concurrency test (99,900 refused, 999 across two lines accepted and collapsed, 1,000 refused) and one conformance check.

  The first draft of that fix rejected duplicate ids outright, which would have been a behaviour change for a client that legitimately sends them; aggregating first is what the existing fingerprint already assumes.

A third pass found three more:

- **P2 — a concurrent request could reuse an idempotency key with a different payload**: the fingerprint was compared in the replay lookup at the top of the transaction, but two requests sharing a key could both pass that lookup before either inserted. The loser then took the insert-conflict path, which returned the winner's order *without* comparing the fingerprint, so it received a success response describing a different cart, address, coupon or payment method. That path now applies the same comparison as the lookup. The existing test for key reuse was sequential and only ever exercised the lookup, so it is joined by a genuinely parallel one that races two different payloads over one key, repeatedly because the interleaving is timing dependent, and asserts that exactly one request creates the order and the loser is refused. Removing the comparison fails it on every run with the loser holding a 200 for the other payload.
- **P2 — the storefront lint failed on an unused import**: `CompleteCheckoutModal.jsx` still imported `newIdempotencyKey` after switching to `getCheckoutIdempotencyKey`, and the lint script treats warnings as failures. Removed. Note that `npm run lint` cannot currently run in this checkout for an unrelated reason: the shared config lives in `frontend/.eslintrc.cjs` while the plugins are installed only under each app's `node_modules`, so ESLint cannot resolve `eslint-plugin-react` from the config's directory. The unused import was verified directly against `no-unused-vars` instead, and is reported both before and after the change.
- **P2 — the storage fallback did not survive a reload**: the key lived only in a module-scoped `Map`, so in a browser that cannot use `sessionStorage`, reopening checkout after a reload produced a new key and could duplicate an order whose response had been lost. `getCheckoutIdempotencyKey` now walks three tiers — `sessionStorage`, then `localStorage`, then memory — and rotation clears all three. The `localStorage` tier is the part that buys reload safety where `sessionStorage` alone is blocked; it is shared with the same customer's other tabs. That sharing was originally justified by claiming two tabs checking out different carts at once contend for one pending key and the loser is refused with 409. That claim overstated what the code could guarantee — the write is not atomic — and it is corrected in the fifth pass below. Where neither store can be used the memory tier is all that remains, and it is now documented as *not* reload-durable rather than implied to be: no client-side code can recover an attempt across a reload without durable storage, so it says so instead of pretending. All three tiers are exercised against the real module, with a reload modelled as a fresh module instance so the memory tier cannot mask a missing storage tier; removing the `localStorage` tier fails that check.

A fourth pass found two more, both in the storage fallback:

- **P2 — reading a storage property could throw before any fallback ran**: `getCheckoutIdempotencyKey` and `rotateCheckoutIdempotencyKey` both iterated `[sessionStorage, localStorage]`. That array is the `for...of` iterable, so both accessors were evaluated *before* the first `try` — and reading either property is itself a guarded browser operation that throws `SecurityError` on an opaque origin or under a storage policy. One blocked area therefore took the whole function down: checkout could throw during render, and rotating the key of a successfully placed order could throw too. Each area is now resolved inside its own guarded access (`availableStorages`), which also skips a name that resolves to something without `getItem`. This was reproduced directly — both functions threw `DOMException` before the change and returned normally after — and the earlier tier tests had missed it because they only made the *methods* throw, never the property access.
- **P2 — the memory tier cannot recover an attempt after a reload**: explicitly **accepted**, not fixed. See "Accepted residual risk" below.

A fifth pass found two more, both in how the storage tiers are searched:

- **P2 — a higher-priority tier could replace an existing pending key**: the tier loop returned from the first store that produced a value and minted into the first store that accepted a write, so a key was only ever recorded in one tier. An attempt that ran while `sessionStorage` was blocked recorded its key in `localStorage`; if `sessionStorage` became writable before the retry, the retry read it empty, minted a fresh key and submitted it — the server saw a new checkout and a lost first response produced a second order. `getCheckoutIdempotencyKey` now searches every available tier first and mints only after all of them come back empty, promoting a key found in a lower tier up into the tiers above it so the tiers cannot diverge. The memory tier is consulted on the same footing and promoted into every store that will accept it, so all three behave consistently. Verified with the two tiers backed by genuinely independent stores — an earlier version of this harness gave both tiers one shared map, which let either tier answer for the other and hid this defect — and the old first-answering-tier behaviour fails it.
- **P2 — concurrent tabs could mint different keys from the same store**: the read-then-write was a non-atomic read-modify-write over a store shared across a customer's tabs, so two tabs reaching checkout before either wrote both read empty, both minted a UUID, and the second `setItem` overwrote the first while each tab returned its own value. Both requests then carried distinct keys and both created orders. Web Storage has no compare-and-set, so this cannot be closed in the client: the chosen remediation narrows it by having the writer re-read after writing and adopt the value actually stored, which resolves the interleaving where the competing write lands between our read and our write. A write landing *after* the re-read is still invisible to that tab, and the doc comment now says so rather than promising a 409. Closing it fully means moving the authoritative pending key server-side, which is the design change described under accepted residual risk. Removing the re-read fails the checks that assert the caller and the store agree.

The last one also corrects a claim the audit previously repeated: that cross-tab sharing of the `localStorage` tier guarantees the loser a 409. It does not, and the code comment asserted a guarantee the code could not keep.

The conformance harness also had a check that encoded the first round's bypass: it submitted bogus client prices with `acceptPricingChange: true` and expected the order to be created. It now asserts the refusal, the reported total, the absence of an order in the refusal body, and that confirming the reported figure places the order at the catalog price.

A sixth pass found two more, both in checkout:

- **P1 — checkout neither validated nor reserved stock**: the order transaction read title/image/price/deletion state only and wrote no inventory change, so a customer could buy more than existed and the displayed count never fell. `decrementStock` now reserves each line with a single conditional `UPDATE ... WHERE stock_quantity >= $1 AND is_deleted = false`, run inside the order transaction on the creator path only (an idempotent replay returns before it). A line that matches no row adds its product id to an `outOfStock` list, and `createOrder` throws a `400` carrying `details.outOfStock`, which aborts the transaction and rolls the inserted order and any partial reservations back with it. Lines are locked in ascending product-id order to avoid deadlocks between multi-line checkouts. `ApiError.badRequest` gained the `options` argument needed to carry the details. The storefront is also told the limit: `getProductDetails` exposes `stock_quantity` as `amount`, `PRODUCT_DETAIL_KEYS` forwards it, and the cart quantity controls pass `maxRange`, matching how the product page already bounds its selector. Note the schema's `stock_quantity >= 0` CHECK already existed and would stop the oversell on its own, but only by rejecting a negative write as a generic `23514`; the guard is the intended path and the one the tests pin, since it returns the structured detail instead. Restock on cancel/delete is deliberately **not** implemented — `setStatus` has no idempotency guard, so crediting stock back could double-count a cancellation; it is a recorded follow-up, not approximated.
- **P3 — cart-add read the wrong Axios error fields**: `CartAPIFunctions.js` read `error.data.response.message`, which normally threw a second `TypeError` before the wrapper's intended result was returned; it now reads `error.response?.data?.message` with a fallback for network errors without a response.

Regression after this pass: backend unit 86/86, integration 35/35 with PostgreSQL (35 clean skips without it), conformance 107/107 on both `:5002` and `:5003`, both frontend builds green, `GeneralFunctions.js` still CRLF. Removing the `stock_quantity >= $1` guard fails both new stock tests; the concurrent-last-unit test asserts the structured refusal specifically, so it distinguishes the guard from the database constraint that would otherwise catch the same oversell.

A seventh pass found one more, in inventory reconciliation:

- **P2 — canceling or deleting an order left its reserved stock deducted**: the reservation was one-way, so a canceled or deleted order kept its units out of the catalog forever. Both paths now reconcile inventory inside a transaction. `restoreStock` credits each line (ascending product-id order, null product ids skipped) and is the inverse of `decrementStock`; `findByIdForUpdate`/`findScopedForUpdate` provide the row lock. `setOrderStatus` restores when a `pending`/`processing` order becomes `canceled`, and, symmetrically, re-reserves when a `canceled` order is reopened — refusing with `400`/`details.outOfStock` if the units are gone — so an order cannot leak inventory by being reopened. `deleteOrder` restores first when it deletes an order still in `pending`/`processing`, which is what the storefront "Cancel order" action (a delete) now does. `delivered` and `canceled` are never restocked. Idempotency comes from the status under a row lock rather than a new column: repeated or concurrent cancels, and a cancel racing a delete, serialize on the order row and return the units exactly once. `PUT /api/orders/:id` can still rewrite items/status without reconciliation, but no client uses it (the admin dashboard uses the status `PATCH` and order `DELETE`), so it is deliberately left alone rather than given a third inventory code path.

Regression after this pass: backend unit 89/89, integration 41/41 with PostgreSQL, conformance 107/107 on both environments, no frontend change. Four mutations pin the new behaviour: no cancel restock (4 failures), restock on every cancel regardless of status (3 failures), no delete restock (1 failure), and no `FOR UPDATE` lock (the concurrent-cancel test fails) — the last one is what distinguishes the lock-based idempotency from reading a stale status.

An eighth pass found three more, closing the last inventory and session gaps:

- **P2 — a canceled order could jump straight to delivered without reserving stock**: `setOrderStatus` re-reserved only when a canceled order moved to `pending`/`processing`, so a direct canceled → delivered admin request was marked fulfilled after its units had already been returned and possibly sold. The restock/consume logic is now keyed by two sets: `STOCK_HOLDING_STATUSES` (`pending`/`processing`) drives the restock into `canceled`, and `STOCK_CONSUMING_STATUSES` (`pending`/`processing`/`delivered`) drives re-reservation out of `canceled`. A canceled → delivered move reserves under the order lock and refuses with `400`/`details.outOfStock` if the units are gone, leaving the status unchanged and nothing reserved. `deleteOrder` keeps the holding set, so a delivered order is never credited. An integration test covers the refusal and the later success.
- **P2 — `PUT /api/orders/:id` bypassed stock reconciliation**: the route's `updateOrder` use case rewrote items/status without locking or adjusting inventory, and no client called it. It is removed along with the repository `update`/`getProductSnapshots`/`mapField` helpers it was the only caller of, and the three unit tests that pinned the allowlisted-column write. A regression test asserts the path now answers `404`.
- **P2 — a remembered profile made an expired session look logged in**: both `IsUserLoggedIn` helpers tested `localStorage` profile data with `||` outside the `&& token` check, so a “remember me” profile kept the UI authenticated after the seven-day token cookie expired. The predicate is now one shared function, `isLoggedIn({ localInfo, sessionInfo, token })` in `frontend/shared_files/General/session.mjs`, returning `Boolean((localInfo || sessionInfo) && token)`; the storefront reads `token`/`customerInfo` and the admin reads `admin-token`/`adminInfo`. A five-case `session.test.mjs` pins it, and both real functions were additionally bundled with stubbed browser dependencies to confirm a profile without a cookie is `false` against the built module.

Regression after this pass: backend unit 86/86 (three `orders update` tests removed with the dead code), integration 43/43 with PostgreSQL, conformance 107/107 on both environments, both frontend builds green, `session.test.mjs` 5/5. Removing `delivered` from `STOCK_CONSUMING_STATUSES` fails the canceled → delivered test, and restoring the `||`/`&&` precedence fails the no-token predicate case.

### Accepted residual risk

Where a browser blocks *both* `sessionStorage` and `localStorage` at the property level, the pending key exists only in the module-scoped `memoryIdempotencyKeys` map and a reload loses it. If an order committed and its response was lost, the next checkout generates a new key and can duplicate the order. This is accepted rather than fixed: recovering it needs a server-managed checkout attempt (a new table, an authenticated endpoint, TTL cleanup for abandoned attempts, and conformance coverage), which is a design change with its own failure modes and contention between two genuine checkouts. The trigger is a narrow conjunction — storage fully blocked, the request committed, the response lost, and checkout reopened.

That same design is also the only way to remove the residual non-atomic write window described in the fifth pass, so the two risks share one remedy rather than standing as separate arguments for and against it. Note the trade-off it introduces is now understood precisely: server-side it would genuinely be one pending attempt per customer and two simultaneous checkouts would collide on purpose, whereas client-side sharing via `localStorage` only *appears* to do that because the write is not atomic. This should be revisited if telemetry ever shows either failure happening.

### Still open

The Node engine (`package.json` declares `^22.22.0`) has not been aligned with the audited runtime (`v20.20.0`). This is a deployment decision, not a defect in the migration: decide which runtime is authoritative, update `engines` accordingly, and keep the two lockfiles (`package-lock.json`, `yarn.lock`) in step.

The storefront lint script also cannot run: the shared config lives in `frontend/.eslintrc.cjs` while `eslint-plugin-react` and `eslint-plugin-react-hooks` are installed only under each app's own `node_modules`, so ESLint cannot resolve them relative to the config file. Either move the config under each app or hoist the plugins to `frontend/`.

The cluster runtime under `/tmp/opencode` is disposable and does not survive a wipe; it is restored from the repo dumps with `npm run db:reinit:local`. The dumps predate `1700000000003_order_checkout_metadata`, so `db:migrate` must be run afterwards or order creation fails with a 500.
